GuildFlow 0.3.0 · plugin de Claude Code

Guía de GuildFlow

Un gremio de agentes que lleva un encargo de programación de principio a fin: plan con criterios verificables, tu aprobación, implementación limitada a rutas concretas, verificación ejecutada por el propio mod, revisión independiente y límites duros de coste, tiempo e intentos.

Probado con Claude Code 2.1.295 Windows, Desktop y CLI Interfaz en español Licencia MIT

1. Introducción

GuildFlow convierte una petición como «añade una función con sus tests» en una misión con reglas que no dependen de la buena voluntad del modelo. Las impone en código un mod de Claude Code:

  • Nadie se aprueba a sí mismo. El plan se aprueba solo en un diálogo tuyo o, si lo activas, automáticamente cuando no toca nada sensible.
  • Cada subtarea escribe solo en sus rutas. El Artífice no puede tocar sus tests, el estado del gremio ni nada fuera de lo aprobado.
  • La evidencia la produce el mod. Las comprobaciones se ejecutan sin shell, con el argv exacto aprobado, y «terminado» exige evidencia positiva en cada criterio.
  • Revisión independiente. Un Paladín, en solo lectura y con su propio contexto, juzga cada criterio con referencias a archivo y línea.
  • Límites que no se pueden desactivar: intentos, iteraciones, tokens, coste equivalente, uso de la suscripción, tiempo, archivos y líneas de diff.

Para quién es: para tareas de programación con un resultado comprobable (tests, scripts de verificación o una interfaz que se pueda mirar en local) en repositorios git de confianza.

2. Cómo funciona

Los roles

Sesión principal

⚖ Maestro

Tu sesión. Interpreta la petición, planifica lo pequeño y coordina. Mientras la misión trabaja usa Sonnet con esfuerzo medium y no escribe archivos ni usa la shell.

Opus · solo lectura

✶ Archimago

Traza todo plan de más de una subtarea: subtareas, rutas, comprobaciones, criterios, recursos y esfuerzo de cada subtarea.

Sonnet u Opus

⚒ Artífice

Implementa una subtarea, solo en sus rutas. Su esfuerzo lo fija el plan (low…xhigh) o la complejidad.

Sonnet · high · solo lectura

⛨ Paladín

Revisa cada criterio con evidencia. En las subtareas visuales tiene que mirar el resultado en el navegador local.

El mod · Haiku opcional

✎ Escriba

Lleva la bitácora y escribe la crónica final. Con escriba: haiku añade un resumen en lenguaje llano.

El ciclo de una misión

PLANNING→AWAITING_APPROVAL→DISPATCH→IMPLEMENTING→VERIFYING→REVIEWING→DONE→LOGGED
  1. Plan. El Maestro planifica si cabe en una subtarea; si no, lanza al Archimago. Si la petición no trae tests, la primera subtarea los escribe, el Paladín los revisa y quedan congelados.
  2. Aprobación. Un diálogo te muestra el plan completo: rutas, argv de cada comprobación, recursos y límites. Si no cabe entero (3000 caracteres), se rechaza para que se divida: nunca apruebas algo que no pudiste leer.
  3. Implementación. Un Artífice por subtarea, en serie. Con maxParallelArtifices > 1, las subtareas independientes pueden avanzar a la vez en talleres aparte.
  4. Verificación. El mod ejecuta las comprobaciones del plan y diff-scope: solo se tocaron rutas autorizadas, el diff no está vacío y respeta los límites.
  5. Revisión. El Paladín juzga los criterios de revisión. Si algo falla, la subtarea vuelve a corregirse con la evidencia (FIXING).
  6. Cierre. Con todo en PASS, el mod escribe la crónica en .guildflow/summary-<id>.md.

Si el mismo fallo se repite, la misión queda BLOCKED y te pide decisión. Si se supera un límite, queda HALTED. Una parada por seguridad (por ejemplo, alguien modificó el estado del gremio) no se reanuda.

Dónde ver el estado

  • Línea de estado bajo el cuadro de texto: trabajando, completada, bloqueada o esperando tu aprobación.
  • Franja encima del cuadro de texto: agentes en curso y siguiente paso.
  • Panel «Gremio · GuildFlow»: la sala del gremio en pixel art, botones de acción, progreso, encargos con el veredicto de cada criterio, tesoro (consumo frente a límites) y bitácora reciente.

3. Instalación

Requisitos

  • Claude Code 2.1.295 o posterior (Desktop o CLI). La API de mods está en acceso anticipado y puede cambiar entre versiones.
  • El proyecto tiene que ser un repositorio git: diff-scope compara con el HEAD aprobado.
  • Los ejecutables que usen tus comprobaciones (por defecto: node, git, tsc, python, py, pytest, cargo, go, dotnet, deno, bun).
  • Añade .guildflow/ al .gitignore del proyecto: ahí van el estado, la bitácora, la evidencia y los talleres.
  • Opcional: Docker, para aislar las comprobaciones (sandbox: docker).

Desde el marketplace

En una sesión de Claude Code en terminal:

/plugin install guildflow --marketplace capibara-html/GuildFlow

Responde y para añadir el marketplace, elige el ámbito (el de usuario es el primero) y ajusta las opciones en la pantalla que aparece. Después puedes cambiarlas con /plugin configure guildflow@guildflow.

El repositorio es privado. Esa orden solo funciona con una cuenta de GitHub que tenga acceso. Para instalarlo en otra máquina sin acceso, usa una copia local del repositorio (abajo) o haz público el repositorio.

Desde una carpeta local

claude plugin marketplace add C:\ruta\a\GuildFlow
claude plugin install guildflow@guildflow

Para desarrollarlo

Carga la carpeta del plugin directamente, sin instalarlo, añadiéndola a CLAUDE_CODE_PLUGIN_DIRS en ~/.claude/settings.json:

{ "env": { "CLAUDE_CODE_PLUGIN_DIRS": "C:\\Users\\<tú>\\Desktop\\GuildFlow\\guildflow" } }

O, para una sola sesión de CLI: claude --plugin-dir /ruta/a/GuildFlow/guildflow. Usa solo una vía: si lo instalas desde el marketplace, quítalo de CLAUDE_CODE_PLUGIN_DIRS, o tendrás dos copias.

Comprobación: escribe /quest-status. Debe responder «Sin misión…».

4. Primera misión

Pide algo con un resultado comprobable. Si ya sabes cómo verificarlo, dilo:

/quest Añade capitalize en src/text/cap.js (primera letra en mayúscula, resto igual, respetando tildes y la cadena vacía) con su test en test-multi/cap.test.js. Comprobación: node --test test-multi/cap.test.js con al menos 2 tests.

Qué pasará:

  1. El Maestro arranca solo, analiza el repositorio y envía el plan.
  2. Aparece el diálogo del plan («Sellar el pergamino» = aprobar). Con autoApprovePlan y un plan no sensible, se aprueba solo.
  3. El Artífice implementa, el mod verifica y el Paladín revisa; lo verás en el panel.
  4. Al terminar tienes la crónica en .guildflow/summary-<id>.md, con cada criterio, su evidencia y el runId de cada ejecución.
Consejo de coste. Lanza las misiones desde una sesión nueva. Cada petición del Maestro arrastra la conversación entera: en una sesión muy larga, la misma misión cuesta varias veces más.

6. Configuración

Instalado desde el marketplace: /plugin configure guildflow@guildflow. Cargado por carpeta: en ~/.claude/settings.json, dentro de pluginConfigs.guildflow.options. El settings.local.json del proyecto no las aplica.

{ "pluginConfigs": { "guildflow": { "options": { "autoApprovePlan": true, "sandbox": "docker", "maxParallelArtifices": 2 } } } }

Un valor fuera de rango se acota a su tope: ningún límite se puede desactivar.

7. Seguridad

Lo primero. Un plugin de Claude Code se ejecuta con tus permisos. Sin sandbox, las comprobaciones ejecutan en tu máquina el código que escribe el Artífice. Úsalo en repositorios de confianza, o activa sandbox: docker.

Lo que el mod impone en código

  • Guarda central de herramientas que falla en cerrado: ante un error, rechaza.
  • Lista blanca por rol, más los recursos aprobados de cada subtarea. Ningún agente puede delegar.
  • Rutas normalizadas (Windows/POSIX, traversal, UNC, ADS, enlaces). Rutas reservadas: .guildflow, .git y .claude.
  • Comprobaciones sin shell, con argv congelado, ejecutables en lista blanca y sin código en línea (-e, --eval…). Se verifica la integridad de los tests antes y después de ejecutarlos.
  • Plan congelado por hash. Si se modifica el estado del gremio fuera del mod, la misión se detiene por seguridad.
  • Acciones sensibles del Maestro (push, despliegue, instalar dependencias, borrados, escribir fuera del repositorio, MCP de sistemas externos): siempre te pregunta.

Sandbox Docker (sandbox: docker)

  • Contenedor sin red, sin capacidades y como el usuario nobody, con límites de CPU, memoria y procesos.
  • El proyecto y la raíz del contenedor van montados en solo lectura; solo /tmp es escribible. Así el código bajo prueba no puede dejar hooks de git ni ajustes de .claude/ que luego corran en tu máquina.
  • Si Docker no responde, la comprobación falla con ese motivo y nunca se repite fuera del contenedor.

Aprobación automática

Dos capas. Primero, la extensión del archivo tiene que estar en autoApproveExtensions. Después, el nombre no puede ser sensible: dependencias, CI o despliegue, migraciones, secretos, configuración del repositorio o del editor, configuraciones de herramientas que ejecutan código (*.config.js, .algorc, conftest.py, setup.py…) o instrucciones de agentes (CLAUDE.md, .claude/, .mcp.json). Se comprueba al aprobar y en cada escritura.

8. Limitaciones por tipo de proyecto

GuildFlow rinde mejor con proyectos que se verifican con un comando que termina solo. Esta tabla resume dónde encaja peor y cómo sortearlo.

Tipo de proyectoEncajeLimitaciónQué hacer
Node / TypeScriptBueno En Windows, npm, npx y node_modules/.bin/* son .cmd y no se admiten. node --test test/ con un directorio no funciona en Windows. Con sandbox, los módulos nativos compilados para Windows no cargan en el contenedor Linux. Declara node con el script real (node node_modules/jest/bin/jest.js) y nombra los archivos de test concretos.
PythonBueno Con sandbox, la imagen por defecto no trae tus dependencias y no hay red para instalarlas. Un venv de Windows no sirve dentro del contenedor. Sin sandbox, usa python o pytest del entorno. Con sandbox, asigna en sandboxImages una imagen propia con las dependencias.
Rust (cargo)Aceptable La compilación puede superar el tiempo de una comprobación (máximo 10 min). Con sandbox, sin red no se descargan crates. Sube timeoutMs en el plan, compila antes fuera de la misión o usa crates vendorizados.
GoAceptable El mod no sabe contar los tests en la salida de go test, así que minTests mayor que 0 falla. Con sandbox, sin red no se descargan módulos. Usa minTests: 0 con stdoutIncludes: ["ok"], o tests con salida TAP. Vendoriza los módulos.
.NETAceptable No hay imagen de serie para el sandbox, y dotnet restore necesita red. Sin sandbox funciona con dotnet test. Con sandbox, añade una imagen del SDK y restaura antes.
Java / Kotlin (Maven, Gradle)Limitado mvn y gradle no están en la lista de ejecutables. En Windows son .cmd o .bat y no se pueden declarar. Su salida («Tests run: N») no se cuenta. Sin red no descargan dependencias. En macOS o Linux, añade el ejecutable a allowedExecutables y usa minTests: 0 con stdoutIncludes: ["BUILD SUCCESS"]. En Windows, de momento, solo revisión del Paladín o un script node/python que lance la herramienta.
Web con interfazBueno Lo visual necesita un servidor de vista previa y solo se mira en localhost. Ese servidor corre en tu máquina, fuera del sandbox. Las subtareas visuales no van en paralelo. Declara preview en el plan (por ejemplo, python -m http.server) y criterios visual. El Archimago lo hace solo.
Juegos y arteAceptable El Artífice escribe texto: no genera imágenes ni audio binarios salvo con herramientas MCP aprobadas (por ejemplo, Aseprite). Los talleres en paralelo copian como texto: un binario se corrompería. Usa formatos de texto (SVG, sprites procedurales) o un MCP como recurso, y no pongas en paralelo subtareas con binarios.
Escritorio o móvil nativoLimitado No hay forma de mirar la aplicación: el navegador del gremio solo abre la web local. Los emuladores y simuladores quedan fuera. Verifica la lógica con tests y deja la interfaz a tu revisión. Para Godot u otros motores, usa su MCP como recurso aprobado.
Con base de datos o servicios externosLimitado Las comprobaciones no tienen shell y no pueden levantar servicios. Con sandbox no hay red. Las migraciones son rutas sensibles. Tests con dobles o bases en memoria (SQLite). Los cambios de esquema, con tu aprobación.
Monorepos grandesAceptable Como máximo 10 subtareas por plan, 30 rutas y 20 criterios por subtarea, 200 archivos y 20 000 líneas por misión. La huella de integridad cubre hasta 300 archivos por ruta protegida. El plan tiene que caber en el diálogo (3000 caracteres). Divide el trabajo en misiones más pequeñas y acota las rutas a paquetes concretos.
Cambios de dependencias, CI o infraestructuraCon tu aprobación Nunca se aprueban automáticamente. Nadie ejecuta npm install ni similares sin preguntarte: el Artífice no tiene shell. Apruébalo en el diálogo e instala tú las dependencias, o deja que el Maestro lo pida.
Sin tests ni forma de verificarAceptable Sin una comprobación ejecutable, la evidencia depende solo de la revisión del Paladín. Deja que la primera subtarea escriba los tests (especificación ejecutable). El Archimago lo propone solo.
Sin git, o con commits durante la misiónNo soportado diff-scope necesita git. Un commit o un reset mientras la misión trabaja mueve el HEAD y hace fallar la verificación. Inicializa git y no hagas commits hasta que la misión termine.

9. Limitaciones generales

  • API de mods en acceso anticipado. Probado con 2.1.295; una versión anterior del CLI da fallos falsos en la validación y en los tests.
  • Sin sandbox por defecto. sandbox: docker requiere Docker funcionando. Quedan fuera del contenedor el servidor de vista previa y el git del propio mod, y el servicio de Docker es privilegiado en tu máquina.
  • Paralelo solo en la implementación. La integración, la verificación y la revisión siguen en serie. No entran las subtareas visuales ni las que comparten rutas. El Artífice en paralelo no puede ejecutar comprobaciones: se verifica al integrar. Todavía no se ha probado en una misión real.
  • Coste de la sesión principal. Crece con la longitud de la conversación; para medir costes reales, usa una sesión nueva por misión.
  • Esfuerzo no confirmable. Se impone en cada petición, pero la respuesta de la API no lo devuelve.
  • Reinicio con un Artífice a medias. Está probado con tests, no en vivo. Los agentes perdidos no se relanzan solos: decides tú con /quest-resume.
  • Tachado de secretos. Solo con patrones conocidos en runs/ y log.jsonl. No pongas secretos en la salida de tus tests.
  • Idioma. La interfaz y el resumen del Escriba están en español.
  • Marketplace privado. La instalación desde GitHub requiere acceso al repositorio.
